# База знаний: Живые отчеты, подотчеты, группы и общая касса

Дата: 2026-05-21
Проект: `finance.brkovic.ltd / FinDesk`
Статус: проектное правило для базы знаний

## Зачем Этот Документ

Этот документ фиксирует логику работы денег, отчетов и прав доступа.

Его нельзя трактовать как временную заметку по интерфейсу. Это базовая модель продукта:

- как администратор ведет свой `Живой отчет`;
- как сотрудник ведет `подотчет`;
- как деньги выдаются сотруднику;
- как остатки переходят дальше;
- как отчеты объединяются;
- как работают группы и роли;
- почему права сотрудника ограничены только внутри конкретной группы.

## Главная Идея

В системе есть не один плоский отчет, а несколько связанных слоев:

```text
Advanced -> Живой отчет -> FinDesk -> общий отчет
```

При этом администратор и сотрудник работают с разными денежными контурами.

Администратор работает со своей доступной кассой группы.

Сотрудник работает только с той суммой, которую администратор выдал ему под отчет.

Деньги, выданные сотруднику, сразу вычитаются из доступной кассы администратора, но не становятся расходом группы до принятия подотчета.

## Пользователь И Группы

Пользовательский аккаунт глобальный.

Один человек может быть участником любого количества групп: не двух и не трех, а хоть двадцати двух и больше.

В каждой группе у него могут быть разные права.

Пример:

```text
Группа A -> base / сотрудник
Группа B -> manager
Группа C -> advanced / администратор
Группа D -> base / сотрудник
...
```

Права из одной группы не переходят в другую.

Если пользователь является сотрудником `base` в группе администратора, это не значит, что весь его аккаунт ограничен. Вне этой группы он может:

- вести личные финансы;
- принять предложение системы и начать осваивать продукт полноценно;
- создать свою группу;
- быть администратором в своей группе;
- быть менеджером или сотрудником в других группах.

Но в конкретной группе, куда его пригласил администратор, он имеет только те права, которые администратор ему дал.

## Приглашение Сотрудника

Администратор создает группу.

Потом администратор приглашает сотрудника по email именно в эту группу.

Приглашение содержит уровень доступа:

```text
base
manager
advanced
```

Сотрудник входит по email и становится участником конкретной группы.

Его права применяются только внутри этой группы.

## Роли В Группе

### Base

`base` - сотрудник на месте.

Он может:

- видеть свой `Живой отчет` / подотчет;
- видеть сумму, выданную ему администратором;
- записывать расходы;
- добавлять фото, сканы, файлы;
- редактировать свои строки до сдачи;
- сверять расчетный остаток с наличными на руках;
- сдавать подотчет администратору.

Он не может:

- заходить в FinDesk этой группы;
- видеть чужие отчеты группы;
- напрямую писать в групповую бухгалтерию;
- выдавать деньги;
- менять роли;
- объединять отчеты.

### Manager

`manager` - промежуточный уровень для FinDesk.

Он может проверять и собирать отчеты там, где администратор дал такие права.

### Advanced

`advanced` - администратор / организатор группы.

Он может:

- создавать и настраивать группу;
- приглашать сотрудников;
- назначать роли;
- вносить деньги в Advanced;
- выдавать деньги сотрудникам под отчет;
- видеть подотчеты;
- принимать или возвращать отчеты;
- собирать общий отчет;
- видеть аудит и расширенную аналитику.

## Денежные Контуры

В системе нужно различать три денежных состояния.

### 1. Общая Касса Группы

Это общий финансовый баланс группы после принятых/включенных отчетов.

Он отвечает на вопрос:

```text
сколько денег осталось у группы в целом
```

Деньги, которые еще находятся у сотрудника под отчетом, все еще являются деньгами группы.

### 2. Доступная Касса Администратора

Это сумма, с которой администратор реально может начинать свой следующий `Живой отчет`.

Формула:

```text
доступная касса администратора =
  общая касса группы
  - фактические остатки открытых подотчетов сотрудников
```

Именно эту сумму должен видеть администратор в своем `Живом отчете`.

### 3. Подотчет Сотрудника

Это отдельная сумма, выданная конкретному сотруднику в конкретной группе.

Сотрудник видит только ее.

Формула:

```text
остаток у сотрудника =
  выданная сумма
  - расходы наличными
```

Безналичные расходы могут фиксироваться отдельно, но физический наличный остаток уменьшают только наличные расходы.

## Cash / Bank Card Как Параллельные Потоки

Правило первого этапа от 2026-05-22:

```text
Живой отчет = Cash stream или Bank Card stream
```

Наличные и банковская карта не смешиваются в одной расчетной карточке.

Перед началом работы пользователь выбирает:

```text
Наличные
Банковская карта
```

### Наличные

Наличный поток имеет входящую сумму и остаток на руках.

Для администратора входящая сумма - доступная касса администратора.

Для сотрудника входящая сумма - выданная ему сумма под отчет.

```text
остаток наличными =
  входящая сумма
  + приход наличными
  - расход наличными
```

### Банковская Карта

Карточный поток не имеет входящей суммы.

Он ведется от нуля в минус:

```text
карточный итог =
  0
  - расходы с карты
```

Карточный поток не уменьшает:

- доступную кассу администратора;
- остаток наличных сотрудника;
- cash-остаток следующей карточки;
- сумму выданного cash-подотчета.

Единственное место пересечения cash и card - сводный отчет:

```text
Наличные расходы
Карточные расходы
Всего расходов
Остаток наличными
```

Подробное правило:

```text
docs/KNOWLEDGE_CASH_CARD_PARALLEL_LIVE_REPORTS_2026-05-22.md
```

## Логика Администраторского Живого Отчета

Администратор вносит сумму в Advanced.

Эта сумма попадает в кассу группы.

Администратор открывает свой `Живой отчет`.

Карточка расходов работает от доступной кассы администратора.

Пример:

```text
Администратор внес: 1000
Доступная касса администратора: 1000
```

Администратор записал расходы:

```text
-100 материалы
-50 топливо
```

После сдачи карточки в отчет:

```text
остаток: 850
```

Этот остаток становится базой следующей карточки администратора.

Если потом администратор добавил деньги в Advanced:

```text
остаток после прошлой карточки: 850
добавлено в Advanced: 500
новая доступная касса: 1350
```

Цикл может продолжаться бесконечно:

```text
внес деньги
-> веду карточку
-> сдаю карточку
-> остаток переходит дальше
-> добавляю деньги
-> новая карточка
```

### Последовательность Карточек Администратора

Карточки администратора в одной группе и у одного владельца идут строго последовательно.

Это не основной пользовательский сценарий, а защитное правило от арифметического коллапса.

Нормальный оператор и так сдает карточки по одной, но система не должна позволять:

- сдать следующую карточку, пока предыдущая уже сданная карточка еще висит в FinDesk на проверке;
- сдать карточки одного владельца в одной группе не по порядку;
- держать две параллельные сданные карточки, потому что у них разные исходные суммы в заголовке.
- автоматически сдавать или подменять предыдущую карточку при попытке сдать следующую.

Причина:

```text
база карточки N+1 =
  остаток после карточки N
```

Если карточка N еще не обработана в FinDesk, карточка N+1 не имеет надежной базы.

Backend обязан запрещать такую сдачу даже при прямом API-вызове.

Интерфейс должен мягко подсветить карточку, которая мешает цепочке. Он не должен сдавать ее автоматически: возможно, ее нужно очистить, удалить или отредактировать.

Текст подсказки должен быть коротким и понятным на мобильном экране:

```text
Обработайте предыдущую запись в FinDesk.
```

Если предыдущая запись еще не должна попадать в FinDesk, оператор должен иметь возможность открыть ее, очистить, удалить или отредактировать.

## Логика Выдачи Денег Сотруднику

Администратор может выдать сотруднику часть денег под отчет.

Пример:

```text
Касса администратора: 1000
Администратор выдал сотруднику: 100
```

После выдачи:

```text
доступная касса администратора: 900
подотчет сотрудника: 100
общие деньги группы: 1000
```

Важно:

```text
выдача сотруднику - это не расход
```

Это перенос денег из кассы администратора в подотчет сотрудника.

Расход появится только тогда, когда сотрудник сдаст подотчет, а администратор его примет.

## Логика Подотчета Сотрудника

Сотрудник получает только выданную сумму.

В своем `Живом отчете` сотрудник не должен видеть всю кассу группы.

Он видит:

```text
выдано: 100
расходы: 0
остаток: 100
```

Сотрудник записывает расходы:

```text
-40 продукты
```

Система считает:

```text
выдано: 100
расходы: 40
расчетный остаток: 60
```

Сотрудник сверяет расчетный остаток с реальными наличными на руках.

Если все верно, он сдает подотчет администратору.

## Принятие Подотчета

Администратор получает подотчет в FinDesk / Advanced.

Администратор может:

- принять подотчет;
- вернуть на исправление.

Если администратор принимает подотчет:

```text
расход сотрудника попадает в общий отчет
```

При этом строка расхода должна сохранить автора:

```text
кто потратил
сколько
на что
из какого подотчета
когда принято
```

Пример:

```text
Администратор внес: 1000
Сотруднику выдано: 100
Сотрудник потратил: 40
У сотрудника осталось: 60
```

После принятия:

```text
общий отчет получает расход сотрудника: 40
у сотрудника остается под отчетом: 60
следующая карточка сотрудника начинается с: 60
доступная касса администратора остается: 900
общая касса группы становится: 960
```

Почему так:

```text
1000 - 40 = 960 общих денег группы
900 у администратора
60 у сотрудника
900 + 60 = 960
```

## Остаток У Сотрудника После Сдачи

Если у сотрудника после принятого отчета остались наличные, они не исчезают.

Они остаются выданными ему деньгами.

Система должна создать / продолжить следующий подотчет сотрудника с этим остатком.

Пример:

```text
старый подотчет:
выдано 100
потрачено 40
остаток 60

после принятия:
новый подотчет сотрудника начинается с 60
```

Новая карточка сотрудника не должна начинаться с нуля, если физически деньги остались у сотрудника.

Техническое правило: после принятия подотчета система автоматически создает следующий открытый подотчет на фактический остаток. Старый подотчет остается принятым/включенным, а новый является резервом денег у сотрудника.

Доступная касса администратора после принятия считается так:

```text
доступная касса =
  общая касса после принятых расходов
  - фактический остаток денег у сотрудников
```

Нельзя продолжать вычитать всю первоначально выданную сумму после того, как расходы уже приняты. Иначе расход будет учтен дважды: один раз как расход группы, второй раз как полный резерв подотчета.

### Возврат Остатка В Кассу

Если сотрудник физически вернул неизрасходованные деньги администратору, это отдельное действие:

```text
Вернуть остаток в кассу
```

Это не расход и не новый доход.

Операция должна:

- закрыть открытый подотчет-остаток сотрудника;
- убрать сумму из резерва сотрудника;
- увеличить доступную кассу администратора на возвращенный остаток;
- не менять общий баланс группы;
- не создавать строку расхода или дохода;
- записать событие в аудит и журнал восстановления.

Действие допустимо только для пустого открытого остатка без строк. Если в подотчете есть записи, его сначала нужно сдать, принять, вернуть на исправление или очистить по правилам цепочки.

## Возврат На Исправление

Если администратор видит ошибку, он возвращает подотчет сотруднику.

Тогда:

- подотчет не попадает в общий отчет;
- расходы не становятся финальными;
- сотрудник снова открывает ту же карточку;
- строки и вложения должны сохраниться;
- сотрудник исправляет и сдает заново.

## Блокировка И Архив Выполненных Карточек

После сдачи карточки в FinDesk она становится закрытой для прямого редактирования.

Это правило действует для всех:

- сотрудник не редактирует сданный отчет напрямую;
- администратор не редактирует сданный или уже включенный в основной отчет напрямую;
- для исправления администратор сначала возвращает карточку на доработку;
- только после возврата карточка снова становится рабочей и редактируемой.

Рабочая логика строится как цепочка должностных этапов:

```text
оператор / живой отчет
-> старший смены / FinDesk проверка
-> начальник отдела / включено в отчет
-> директор / итоговый отчет
```

Миссия этой цепочки - не допустить искажения цифр. На каждом этапе человек должен легким действием открыть, проверить и вернуть данные назад до момента отдачи конечной информации.

Если карточка уже включена в основной отчет, она считается выполненной.

В живом журнале такая карточка должна быть визуально приглушена как завершенная.

Выполненную карточку можно убрать с рабочего экрана в архив. Это только UX-очистка:

```text
архив выполненной карточки не меняет reportable,
не меняет суммы,
не меняет общий отчет,
не меняет базу следующей карточки
```

Архив выполненных живых отчетов - это не этап FinDesk и не меняет цепочку отчетов.

В визуальном ряду FinDesk первая карточка `Текущий отчет` не нужна: она дублирует живой журнал и создает шум. Рабочий ряд должен состоять из трех понятных блоков:

```text
02 Сданные отчеты
03 Включено в отчет
04 Общий архив
```

`Общий архив` стоит крайней правой карточкой и показывает количество заархивированных записей. При открытии администратор видит:

- мой архив;
- папку архива каждого сотрудника в группе;
- внутри папки - карточки владельца с суммами и датой архивации.

Архив нужен для чистки рабочего экрана и первичной защиты оперативной информации.

Архивация выполненной карточки не должна убирать ее из блока `Включено в отчет`. Если карточка уже включена в отчет, она остается в этом рабочем пакете до подготовки / сохранения итогового отчета.

Блок `Включено в отчет` показывает количество карточек, включенных в рабочий пакет. В модалке администратор видит конкретные карточки и может вернуть их назад во второй этап `Сданные отчеты` на доработку.

Смысл блока `Включено в отчет` - подготовка красивого информационного Excel / печати / сохранения сведенного отчета. Сам сведенный отчет хранится уже на странице `Отчеты`.

Общий архив группы в FinDesk видит только администратор.

Модалка просмотра карточки не должна смешивать действия разных этапов:

- карточка `На проверке в FinDesk`: администратор видит только возврат на исправление; сотрудник видит только запрос исправления;
- карточка `Включено в отчет`: администратор сначала возвращает ее в FinDesk-пакет / сданные отчеты, а не сразу в живое редактирование;
- архив не является действием внутри модалки проверки;
- удаление не показывается для сданных или включенных карточек.

Запрос сотрудника должен называться `Запросить исправление`, а не `Запросить возврат`. Это действие показывается на самой карточке сотрудника в живом журнале, а не внутри администраторской модалки просмотра.

Личный архив выполненных живых отчетов доступен каждому владельцу карточек. Администратор дополнительно видит архив группы в FinDesk.

В архиве обязательно сохраняется пометка:

```text
чей живой отчет
какая карточка
когда убрана с рабочего экрана
какие суммы были / стали
```

Сотрудник после сдачи может только просматривать закрытую карточку.

Если сотрудник увидел ошибку после сдачи, он не возвращает карточку сам. Он отправляет запрос администратору на возврат карточки на доработку.

## Безопасный Журнал Восстановления

Для живых отчетов нужен отдельный серверный журнал восстановления.

Он не заменяет базу данных и не участвует в расчетах. Его задача - дать администратору ручной способ восстановить картину, если произошел сбой, ошибка интерфейса или повреждение рабочей цепочки.

Правило:

```text
каждое важное действие с живым отчетом пишется автоматически
```

Журнал должен быть максимально простым и безотказным:

- append-only JSONL файл в приватной папке `storage`;
- одна строка файла = одно событие;
- запись через file lock;
- ошибка записи журнала не должна ломать основную операцию;
- параллельно администратор может выгрузить CSV-таблицу из FinDesk.

В событии обязательно сохраняются:

```text
дата события
группа
исполнитель
email исполнителя
id карточки
текущее состояние карточки
строки карточки
суммы было / приход / расход / остаток
сдано / не сдано / включено / возвращено / отменено / архив интерфейса
кто совершил действие
```

Для просмотра и ручного восстановления удобнее не делать колонку на каждого сотрудника. При 22+ сотрудниках такая таблица станет широкой и хрупкой.

Более надежный формат:

```text
одна строка = одна запись или событие
отдельные колонки = дата, исполнитель, карточка, статус, сумма, описание
```

Такой CSV легко открыть в Excel/Sheets, отфильтровать по сотруднику, дате, статусу или карточке и вручную восстановить данные.

## Слияние В Общий Отчет

Общий отчет собирается из:

- принятых карточек администратора;
- принятых подотчетов сотрудников;
- строк расходов с указанием автора;
- вложений и документов.

Общий отчет не должен терять источник строки.

Нужно видеть:

```text
расход администратора
расход сотрудника A
расход сотрудника B
расход сотрудника C
```

Это особенно важно, потому что сотрудников и групп может быть много.

## Правила Для Интерфейса

### Администратор

В `Живом отчете` администратора показывается доступная касса администратора.

Она уже должна учитывать:

- остаток после предыдущей принятой/сданной карточки;
- добавленные деньги из Advanced;
- деньги, выданные сотрудникам под отчет.

### Сотрудник

В `Живом отчете` сотрудника показывается только его подотчет.

Он не должен видеть:

- всю кассу группы;
- FinDesk группы;
- Advanced группы;
- чужие подотчеты;
- административные действия.

### Открытие Существующего Подотчета

При нажатии на сохраненную карточку должна открываться именно эта карточка.

Она должна открываться:

- с исходной выданной суммой;
- со всеми строками;
- с вложениями;
- с возможностью редактирования, если отчет еще не принят;
- с возможностью удаления/исправления по правилам доступа.

Нельзя открывать пустую новую карточку вместо выбранной.

## Правила Для Реализации

- Выдача денег сотруднику сразу уменьшает доступную кассу администратора.
- Выдача денег сотруднику не является расходом группы.
- Расход появляется только после принятия подотчета.
- Остаток сотрудника после принятия становится началом следующего подотчета.
- Base-сотрудник не получает доступ в FinDesk группы администратора.
- Права всегда считаются внутри конкретной группы.
- Один пользователь может состоять во множестве групп с разными ролями.
- Подотчеты разных групп не смешиваются.
- Деньги разных групп не смешиваются.
- Отчеты разных групп не смешиваются.
- Каждая строка общего отчета должна сохранять автора.

## Короткая Формула

Для администратора:

```text
моя доступная касса =
  деньги группы
  - фактические остатки открытых подотчетов сотрудников
```

Для сотрудника:

```text
мой подотчет =
  деньги, которые мне выдал администратор в этой группе
  - мои расходы
```

Для общего отчета:

```text
общий отчет =
  принятые расходы администратора
  + принятые расходы сотрудников
  с сохранением автора каждой строки
```
